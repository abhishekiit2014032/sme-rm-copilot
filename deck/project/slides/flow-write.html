The follow-up agent is the only path that writes to a bank system, so this is the one an architecture board will test hardest. Same grid as the read path, same private network boundary. One: the RM pastes meeting notes; voice memos come in Phase 2. Two: before any model call, the orchestrator runs Prompt Shields on the user prompt, quarantines any quoted instructions, for example an email that says ignore your rules, and masks PII with AI Language plus regex. Three: through the APIM AI gateway, gen-small extracts JSON drafts: the call report, tasks and signals. They are validated against a schema and a policy check, so no approval, pricing or limit commitments. Four: the drafts come back to the RM, who edits them. Nothing has been written anywhere yet. Five: the RM clicks Approve. web-bff checks Origin and the CSRF token and requires a fresh sign-in through Conditional Access, otherwise it asks for step-up. Six: web-bff canonicalises the final draft, hashes it, and asks Key Vault to sign an ES256 approval token inside the HSM. The token names the RM, the customer, the operation and the draft hash, expires in five minutes and has a one-time id. Seven: the orchestrator passes the draft and the token to tool-gateway. It cannot mint or alter a token, because it has no key at all, and neither does the model. Eight: tool-gateway verifies the signature with the public key only, then checks the RM against the token on the call, the customer, the operation, the hash of exactly what was submitted and the expiry, and records the one-time id in Cosmos DB. A second use is rejected as a replay. Nine: the call report and each task go to the CRM through APIM with an external reference. If the CRM times out, the item goes to the Cosmos outbox and a worker reads before it retries, so nothing posts twice. The RM sees committed, queued or failed per item. Ten: audit events record the approval and each write. The customer email is never sent by the copilot: it opens in Outlook as a draft and the RM sends it.
