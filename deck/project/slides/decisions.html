Five design decisions and what we traded off

DecisionOur choiceAlternativeWhy
GroundingRAG on Azure AI Search + live tool callsFine-tune the modelFresh data, citations, access control at source; fine-tune later only for tone or format
Customer dataLive APIs via tool-gateway, as the RM (OBO)Embed it in a vector indexNo PII copy; entitlements and freshness come from the source system
Agent designOne orchestrator, fixed workflows, typed toolsMulti-agent frameworkEasier to test, trace and explain to auditors and model-risk teams
Model hostingAzure OpenAI Regional in UAE NorthGlobal or Data Zone deploymentInference stays in the UAE; no cross-border failover, a model outage means degraded mode
Write actionsDraft + RM approval signed in Key Vault HSMAutonomous writesRM stays accountable; the orchestrator and model cannot forge an approval

These are the decisions an architecture review board will challenge, now in their Azure form. Grounding: retrieval on Azure AI Search and live tool calls rather than fine-tuning, because policies and customer data change daily, a fine-tuned model cannot cite its sources, and it cannot enforce access control. Customer data: we query it live through tool-gateway with the RM's own on-behalf-of token instead of embedding it, so there is no second copy of PII to secure and access rules come from the source system. Agent design: one orchestrator with fixed workflows and typed tools is less fashionable than a multi-agent system, but far easier to test and explain. Model hosting: Azure OpenAI Regional deployments in UAE North, so inference stays in the country. We deliberately give up cross-border failover: if the model is unavailable the copilot runs in degraded mode, with a data-only brief, ranked passages or a manual call report. Writes: a human approves every change, and the approval is an ES256 token signed in the Key Vault HSM by web-bff. tool-gateway only holds the public key, so neither the orchestrator nor the model can approve on the RM's behalf.
