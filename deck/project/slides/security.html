2 · SECURITY AND ACCESS CONTROL

The model never decides who can see what

Identity and entitlements

The RM’s identity flows end to end. Tools enforce portfolio and role rules in code, never in the prompt.

Data protection

Hosted in UAE North, PII masked before the model, no training on Bank data; abuse-monitoring storage off by exemption.

Prompt-injection defence

Documents and emails are treated as data, not instructions. Tool allow-list and output checks.

Least-privilege writes

Write APIs accept only a draft plus a signed RM approval. Separate service identities for read and write.

Audit trail

Every prompt, retrieval, tool call and approval is audited: tamper-evident trail, encrypted content.

Model and vendor risk

Third-party risk review, contractual data terms, model inventory, and a kill switch per use case.

The headline principle: access control is enforced by deterministic code at the tool and data layer, using the RM’s own identity, never by instructions in a prompt. If an RM asks about a customer outside their portfolio, the API returns “not authorised” and the model has nothing to leak. That is also our main defence against prompt injection: even if malicious text in a document or email tricks the model, the model has no more privilege than the user, and it cannot approve its own writes. On data protection, Azure OpenAI runs as a Regional deployment in UAE North on a private endpoint, with store set to false, and Microsoft does not train on our prompts. By default Microsoft abuse monitoring can keep prompts for up to 30 days, so the modified abuse monitoring exemption is a go-live gate before any real data. PII that the task does not need, for example ID numbers, is masked before it reaches the model. Everything is logged for audit, and each use case can be switched off independently.
