PRINCIPLE

Customer data is never copied into a vector store. It is read at question time with the RM’s own permissions, so access rules and freshness come from the source system.

Having seen where everything runs, here is what the copilot actually reads and writes. Two integration patterns, chosen per data type. Structured customer data, such as balances, limits and KYC status, is fetched live through tool-gateway and the APIM system facade, from a read replica where the core system cannot take the load. That keeps it fresh and lets the source system's entitlements apply. Unstructured content that is not customer-specific, such as policies, product guides and circulars, goes through an ingestion pipeline into Azure AI Search, with version and effective-date metadata. The calendar is read through Microsoft Graph with the narrowest scope, Calendars.ReadBasic, as the RM. The copilot has no mail scope: an approved customer email opens in Outlook through a compose link and the RM sends it. Integration effort is usually the long pole in these programmes, which is why discovery starts with an API inventory: which of these already have usable APIs and which need an ODS or a new service. Each of these systems has an interface agreement with an availability and latency budget, summarised later in the deep dive.
